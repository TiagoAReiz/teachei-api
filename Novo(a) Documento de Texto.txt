📄 PRD: Projeto Findable (O Marketplace Invertido)
Status: Definição de MVP
Stack: Java (Spring Boot) | Next.js | Expo | Azure | NoSQL
Versão: 1.0
________________________________________
1. Visão Geral
O Findable é uma plataforma onde o comprador é o protagonista. Diferente de marketplaces tradicionais (Webmotors, OLX), aqui o comprador anuncia seu desejo de compra (intenção), especificando o que procura. Isso inverte o funil de vendas, entregando leads qualificados para vendedores e concessionárias.
2. Objetivos do MVP
•	Validar a disposição do usuário em pagar para anunciar uma intenção de compra.
•	Implementar uma arquitetura escalável (Hexagonal) que permita novos nichos.
•	Centralizar a busca de veículos através da integração com a Tabela FIPE.
•	Garantir uma experiência cross-platform (Web e Mobile).
________________________________________
3. Personas
1.	O Comprador: Indivíduo que sabe o que quer, tem pressa ou não tem tempo de garimpar anúncios. Está disposto a pagar uma pequena taxa para que o produto "venha até ele".
2.	O Vendedor (Lead Receptor): Lojistas ou particulares que possuem estoque e buscam compradores ativos para girar o capital rapidamente.

🛠 Especificação Detalhada: Projeto Findable
1. A Proposta de Valor: "O Inverso do Marketplace"
O Findable resolve o problema da "procura infinita". Em vez de um comprador passar semanas filtrando anúncios de vendedores que muitas vezes já venderam o veículo ou não respondem, o comprador publica um Ticket de Intenção de Compra.
Vendedores (concessionárias e particulares) usam o Findable para encontrar liquidez imediata, indo direto a quem já declarou que tem o dinheiro e o interesse.
________________________________________
2. Experiência do Usuário (UX) e Funcionalidades
2.1. O Fluxo do Anunciante (Comprador)
O anúncio de compra é guiado e parametrizado para evitar dados "sujos":
1.	Seleção de Categoria: O usuário escolhe entre Carro, Moto ou Caminhão.
2.	Integração FIPE: Ao começar a digitar a marca, o app consome o FipeAdapter para listar marcas, modelos e versões oficiais. Isso garante que o anúncio seja categorizado corretamente para o filtro do vendedor.
3.	Flexibilidade de Escolha (Multi-select): Diferente de um anúncio de venda, aqui o comprador pode aceitar variações.
o	Exemplo: "Aceito Corolla dos anos 2020, 2021 ou 2022 nas cores Branco ou Prata".
4.	Definição de Budget: O usuário insere o valor que pretende pagar. O sistema exibe o preço da Tabela FIPE atual como referência para evitar ofertas irreais.
5.	Checkout: Integração com Gateway para pagamento do anúncio (Modelo Pay-per-Ad).
2.2. O Perfil e Contato
Após o pagamento, o anúncio fica público. O perfil do anunciante exibe:
•	Nome e reputação (estrelas).
•	Botão direto para WhatsApp (usando o protocolo api.whatsapp.com).
•	Links para redes sociais (Instagram/Facebook) para gerar confiança entre as partes.
________________________________________
3. Arquitetura de Software (O "Motor" Java)
Adotaremos a Arquitetura Hexagonal, garantindo que o núcleo do negócio seja imune a mudanças de tecnologia.
3.1. Core Domain (O Coração)
No centro, teremos a entidade Anuncio. Ela não contém anotações de banco de dados (JPA ou NoSQL). Ela é um POJO puro. As regras de negócio, como "um anúncio deve ter pelo menos um ano selecionado" ou "o preço não pode ser 0", residem aqui.
3.2. Estratégia de Persistência Poliglota
•	PostgreSQL (Relacional): Utilizado via Spring Data JPA. Focará na gestão de Identidade e Acesso (IAM). Armazenará tabelas de Usuario, Perfil, TransacoesPagamento e NiveisAcesso.
•	NoSQL (Document Store): Utilizado para a entidade Anuncio.
o	Por que? Cada nicho (Veículos agora, Imóveis depois) tem atributos diferentes. O NoSQL permite salvar um mapa de atributos dinâmico sem a necessidade de migrações de esquema (Flyway ou Liquibase) constantes.
o	Estrutura do Doc: O documento conterá metadados fixos (ID, UserID, Data) e um objeto especificacoes que muda conforme o nicho.
3.3. Segurança com Auth0
Utilizaremos o Auth0 para delegar a autenticação.
•	O Frontend obtém um JWT.
•	O Backend (Spring Security) valida esse token em cada requisição através da chave pública do Auth0.
•	Isso remove a carga de gerenciar senhas e segurança complexa no nosso banco.
________________________________________
4. Stack Tecnológica e Infraestrutura
4.1. Backend Java Extensions

1. Estrutura de Pastas (Arquitetura Hexagonal em Java)
No Java (Spring Boot), a ideia é proteger o teu Core de influências externas. O código de negócio não deve saber que o banco de dados é o CosmosDB/DynamoDB ou que a API de carros é a FIPE.

2. Estratégia de Busca e Filtros Dinâmicos (NoSQL)
Como queres permitir filtros por múltiplos anos, cores e modelos, a modelagem no NoSQL deve ser pensada para Query Efficiency.
Estrutura do Documento (Exemplo JSON):
JSON
{
  "id": "uuid",
  "userId": "auth0|id",
  "nicho": "VEICULO",
  "status": "ATIVO",
  "detalhes": {
    "tipo": "CARRO",
    "marca": "Toyota",
    "modelo": "Corolla",
    "anos": [2020, 2021, 2022],
    "cores": ["Branco", "Prata"],
    "precoMax": 120000.00
  },
  "contato": {
    "whatsapp": "5511999999999",
    "instagram": "@user"
  }
}
Estratégia de Filtro:
•	Query por "Array Contains": Tanto no DynamoDB quanto no CosmosDB, podes fazer queries que verificam se o valor do vendedor (ex: 2021) está contido no array de interesses do comprador (anos).
•	Índices (GSI): No DynamoDB, terias de criar um Global Secondary Index por nicho + status.
•	Filtro Dinâmico: No backend, construirás um QueryBuilder. No Spring Data NoSQL, podes usar o Query dinâmico para adicionar cláusulas conforme o utilizador preenche os filtros no Next.js/Expo.
________________________________________
3. Integração com API de Modelos (FIPE e afins)
Para o MVP, recomendo não apenas "consumir", mas encapsular essa API para não ficares refém dela.
A Porta (VehicleDataPort):
Java
public interface VehicleDataPort {
    List<Marca> getMarcas(TipoVeiculo tipo);
    List<Modelo> getModelos(String marcaId);
    List<Ano> getAnos(String marcaId, String modeloId);
    PrecoMedio getPrecoFipe(String marcaId, String modeloId, String anoId);
}
O Adaptador (FipeAdapter):
Podes usar uma API pública (ex: https://deividfortuna.github.io/fipe/) ou a oficial.
•	Caching: Informação da FIPE não muda a toda a hora. No teu adaptador, utiliza o @Cacheable do Spring com um TTL (Time To Live) de 24h ou mais. Isso evita chamadas desnecessárias e torna o teu front-end (Next.js) instantâneo nos combos de seleção.
•	Resiliência: Usa o Resilience4j (Circuit Breaker). Se a API da FIPE cair, o teu app não pode travar. O utilizador deve conseguir digitar o modelo manualmente se o serviço externo falhar.
________________________________________
Dicas extras para o teu MVP:
1.	WhatsApp Deep Link: No perfil do anunciante, não coloques apenas o número. Gera o link https://wa.me/numero para que o vendedor clique no app e abra direto a conversa.
2.	Next.js + Expo: Como vais usar Next.js, aproveita as Server Components para renderizar a lista de anúncios (SEO é importante aqui para os compradores encontrarem o site no Google). No Expo, foca na experiência de notificações (Push) quando houver um match.
3.	Kubernets (AKS): Começa com o Horizontal Pod Autoscaler (HPA) configurado pelo uso de CPU. Como esperas picos de acesso quando enviares notificações, o K8s vai escalar o teu Java automaticamente.
